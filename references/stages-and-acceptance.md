# 阶段名称、输入与完成定义

这些名称用于清楚协作，不宣称行业存在唯一的标准分期。“信息解析完成”通常只到第 2 项；“能编译”通常只证明第 3/4 项的一部分。

| 节点 | 做什么 | 产物/完成证据 | 典型误区 |
|---|---|---|---|
| 输入取证与基线固定 | 识别包、版本、split/asset packs、引擎和原运行节点 | 输入哈希、来源、版本、只读原件；原包观察与条件 | 混用不同版本或把调试包当未经修改原包 |
| 资源、类型与代码证据解析 | 提取场景/Prefab/配置/媒体、类型字段、原生或托管实现依据 | 可追溯资产、metadata/字段映射、方法地址/程序变体 | 把签名与空方法、原生区间数量当完整源码 |
| 工程图重建与依赖绑定 | 恢复资产身份、序列化引用、官方库身份、构建场景与配置 | 原 GUID/fileID 对照、引用有效、真实组件、可导入工程 | 同名空壳使 Missing Script 归零，或另造启动场景 |
| 可执行语义重建 | 让脚本、Shader 和初始化正确使用原信息 | 分支/状态/副作用契约、可读实现、必要夹具 | 按玩法印象写相似游戏；原参数保留但消费者未实现 |
| 差分验证与等价性闭合 | 对齐原版与恢复版同条件运行状态、视觉和时序 | 与源码及实包绑定的限定范围回执 | 用编译或 Null 图形通过证明画面；不同状态截图比较 |
| 可维护源码交付 | 让其他人理解、修改、构建、复验，并知道边界 | 自包含工程、依赖与构建说明、语义账本、匹配产物、已知缺口 | 宣称得到原作者仓库；可读性重构后未再验行为 |

工程图、语义和验证相互反馈，不能机械地等“所有资源/方法解析 100%”才启动重建。已知资源完整而 Shader 消费者错误，应沿渲染链推进，不重开解包。

## 定义“100%”

先定义范围集合，随后追踪每一项的证据强度和未知项。可选维度如下，按项目删减/补充，用户排除的项单独标记：

- 正式启动、菜单导航、教程和输入拒绝分支。
- 全部关卡数据及不同机制/特殊对象；关卡数据完整与全部关卡运行验收分开。
- 物理/移动/交互规则、动画、特效、音频与生命周期。
- 布局、相机、安全区、分辨率/方向分支、UI 文本与交互。
- 胜负、奖励、重试、切关、保存/冷启、进度恢复。
- 图形 API/GPU、资源采样/Shader、平台/依赖配置；性能/稳定性按承诺范围。
- 服务端依赖、广告/购买回调、真实 SDK 等按用户边界分别处理。
- 可读性、可构建性、可复验性与交接完整性。

状态至少区分：未观察、静态证实、限定运行证实、范围内验收、范围外、外部阻塞。可采用项目现有状态名称，不另起互相冲突的总控系统。

没有分母、没有对未覆盖分支作说明时，不给“恢复 95%”等总百分比。全关卡文本可读 ≠ 全关卡可玩；方法有入口视图 ≠ 方法语义恢复；局部 ROI 低误差 ≠ 全画面/全设备等价。

原作者局部变量名、注释、组织历史和优化消除代码通常不可唯一反推。交付承诺应是“根据原证据重建的可读源码及范围内等价性”，而不是逐字原始源码。对无法获取的服务端行为保持未知，不用客户端字符串替代。
